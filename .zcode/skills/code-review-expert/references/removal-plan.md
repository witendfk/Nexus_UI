# SDK 删除与迭代计划

## 候选判断

- 业务 prompt、模型装配、固定流程 Policy、示例 Catalog、环境读取和 listener：优先迁至参考应用，保持示例可运行。
- 重复 guard、绑定解释与 SSE 消费逻辑：在共享契约与等价测试建立后合并，避免同时维护两套公共规则。
- 硬编码组件/业务名分支、模块全局 store、隐式默认值：用声明与显式装配替代，不因删除而失去安全基线。
- 无消费证据的抽象与导出：查调用方、公开契约和文档后再删，内部无引用不证明外部无人使用。
- 目标落地后更新现状、差距、任务与迁移说明；保留注明日期的历史证据，不将目标文档变成第二套事实源。

## 每项给出

1. 收益与风险：消除什么耦合/重复；公开 API、现有消费方和行为受到什么影响。
2. 证据与替代：真实引用路径、可达性；迁移、弃用或保留方案及选择理由。
3. 实施顺序与验收：先建立什么契约/测试，再迁移哪些 SDK 调用方，什么证据算完成。

优先级依据实际影响采用 P0–P3，不把所有死代码机械列为高优先级。删除/迁移不自动授权改码或发版；按用户当前授权执行。workspace、产物、版本与提交规则读取根 AGENTS.md，不在 skill 固化 tarball 仪式。

计划只覆盖 SDK 及其契约验收载体。接入方的业务工程、Agent 选型、数据库迁移和部署改造不列为 SDK 评审整改项。
