# PRD — Nexus UI SDK

更新：2026-10-30。本文定义产品目标与验收要求；当前实现、目标契约、结构、决策和进度分别见 [SPEC](SPEC.md)、[ARCHITECTURE](ARCHITECTURE.md)、[DESIGN](DESIGN.md)、[CURRENT](tasks/CURRENT.md)。本文的要求不代表能力已经交付。

## 1. 产品定位

**Nexus 是可嵌入宿主应用、由宿主声明能力边界的 Agent UI Runtime SDK。** 它把不可信的 A2UI 候选消息转为可校验、可交互、可持续更新的任务界面。宿主保留自己的页面布局、设计系统、Agent、身份权限和业务后端。

产品价值是让一份宿主契约贯通生成提示、候选输出准入、数据绑定、渲染和 action 回流。SDK 提供协议运行时、准入机制与可靠的界面生命周期；业务对象、业务判断与副作用由宿主负责。SDK 可以调用宿主注册的 handler，handler 的业务实现归宿主所有。

首发用户是已有 React 应用和 Node 后端、希望嵌入 Agent 交互界面的开发者。首发支持显式声明的 A2UI v0.9 子集，不宣称完整官方 Basic Catalog 兼容。开源展示与面试是项目用途；质量以接入契约和可复核证据衡量。

### 1.1 要解决的问题

1. 模型能输出 JSON，但宿主还需确认其组件、字段、绑定与 action 是否可用。
2. 已有应用需要把 surface 放进自己的布局，并复用自己的组件和表单控件。
3. 流式预览、已提交界面和业务结果有不同生命周期；每个宿主重复接线容易误判完成、遗留可点击预览或丢失最新输入。
4. Agent、transport 和 HTTP 框架变化时，协议与准入行为应保持一致。

成功体验：开发者定义 Catalog 和 renderMap、配置生成源与 action handler，将 surface 放入已有页面；SDK 负责通用解析、校验、输入准入、运行状态与失败清理。开发者无需复制 SSE 状态机或修改 SDK 内核来增加自定义控件。

## 2. 责任边界

| 责任       | SDK                                                        | 宿主 / Agent / 示例                            |
| ---------- | ---------------------------------------------------------- | ---------------------------------------------- |
| 消息与组件 | 协议/Profile、生命周期、Catalog schema、结构化 diagnostics | 宿主声明可用组件、字段与 action                |
| 输入       | 绑定解释、声明过的可编辑路径与值类型校验、最新输入提取     | 宿主决定哪些字段可编辑及业务有效性             |
| action     | 来源/声明/界面 revision 核对、参数准入、分发与关联标识     | 身份权限、对象归属、领域幂等、业务事务及执行   |
| 生成       | 可注入的候选消息源、取消、资源限制、输出准入               | 模型选择、业务 prompt、工具、记忆及 Agent 编排 |
| 渲染       | surface 订阅、组件映射、输入绑定与交互门控                 | 页面布局、设计系统、业务组件实现               |
| 恢复       | 报告运行结果、界面提交状态和失同步；提供恢复入口           | 查询业务结果、决定是否重试或重新生成           |

Agent 输出与浏览器输入都不是业务事实。Catalog hash 表示契约内容一致，不证明来源可信或用户获授权。安全默认值、原型防护、URL 使用限制、正则与资源预算属于 SDK；具体身份与业务授权由宿主提供。

## 3. 产品组成与目标接入

### 3.1 目标组成

| 包                 | 职责                                                                        | 当前情况                          |
| ------------------ | --------------------------------------------------------------------------- | --------------------------------- |
| `@nexus-ui/core`   | 框架与传输无关的协议、Catalog、绑定、surface 状态和 action 事件             | 已有；Catalog v2 与通用交互扩展已交付（S2） |
| `@nexus-ui/client` | 框架无关的浏览器会话；fetch/SSE 适配、终态识别、预览/提交、取消及交互门控   | 已交付并阶段验收；会话/传输、隔离与恢复（S4）    |
| `@nexus-ui/react`  | Provider、按 surface 渲染的视图、hooks、标准与自定义组件映射                | 已交付并阶段验收；Provider/Surface 与联合接入（S4） |
| `@nexus-ui/server` | 框架无关的 guard、运行调度、action 准入和状态；可选 Koa/SSE 与外部 RPC 适配 | 已有；通用运行模块与 Koa 薄适配已交付（S3）   |

当前为 core/client/react/server 四个私有包，client 与 React 组合已完成 S4 阶段验收。client 抽取自两处浏览器的重复会话逻辑，两处消费方已统一迁移；实际浏览器关键路径与限制见 [S4-ACCEPTANCE](tasks/S4-ACCEPTANCE.md)。仓外安装与最终发行门禁仍归 S5。guard、Catalog、Policy 暂作为包内模块维护；结构见 ARCHITECTURE，依据见 DESIGN。

### 3.2 最小接入旅程

1. 宿主定义版本化 Catalog：展示组件、自定义输入、可挂载 action 的组件、输入与参数约束。
2. 宿主注册 renderMap，并创建显式注入生成源与 handler 的 server runtime。
3. 浏览器创建 client session，把 session 的 runtime 交给 React Provider；在自己的布局中挂载指定 surface。
4. 候选消息经 guard 后展示为不可提交的预览；收到成功终态后界面可交互。
5. 用户编辑输入并触发 action；SDK 验证声明和输入，宿主校验业务事实并执行，patch 经 guard 后更新原 surface。
6. 失败、取消或缺失终态时，SDK 清理本次预览并报告界面是否失同步；宿主使用关联标识恢复业务结果。

直接消费 core 的本地应用仍可自行决定消息来源和交互处理，不必接入 client 或 server。参考 Agent、内置模型和固定路由均不构成使用 SDK 的前置条件。

## 4. 必须交付的能力

| ID  | 需求                   | 验收结果                                                                                                 |
| --- | ---------------------- | -------------------------------------------------------------------------------------------------------- |
| R1  | 受约束协议运行时       | JSONL 跨 chunk、消息顺序、surface 隔离、dataModel 和 VNode 更新确定；拒绝消息不落状态                    |
| R2  | 同源能力契约           | Catalog schema、绑定、action 和 prompt contract 一致；前后端共享可复用校验规则，宿主 Policy 经显式注入   |
| R3  | 可嵌入 React 视图      | Provider 不决定布局；两个 surface 可独立挂载、更新和删除；配置重渲不意外重建 runtime；自定义设计系统可用 |
| R4  | 完整交互扩展           | 新增展示、输入和 action 组件只需声明与注册；最新合法输入到达 handler；未声明字段、路径和类型被拒         |
| R5  | 明确运行与失败语义     | 预览不可提交；EOF 不等于成功；失败/取消清理预览；失同步阻止旧界面继续 action；流结果与业务结果分开       |
| R6  | 可组合服务端           | 相同候选流与 action 在 Koa 和非 Koa 消费中得到相同准入/提交结果；宿主自选 Agent、handler 和状态实现      |
| R7  | 可安装、可诊断、可维护 | 当前产物仓外安装、公开 API/types/exports/依赖兼容、结构化诊断、conformance、资源反例和 CI 门禁可复现     |

R2/R4 的组件能力校验不替代宿主业务授权。R5 的恢复承诺覆盖 SDK 状态和恢复接口；SDK 不建设通用业务结果库、不承诺业务 exactly-once。

R5 的 action 基准须绑定浏览器实际渲染的运行提交结果。同一 surface 被另一运行更新后，查询最新 revision 不能给旧界面恢复提交资格；SDK 应拒绝旧基准，并通过重新生成或受控快照恢复视图与基准的一致性。

## 5. 验收场景与发布门禁

### 5.1 SDK 独立宿主验收

在仓外干净 React + Node 项目仅使用公开入口完成以下用例：

- 自有布局中同时挂载两个 surface，更新或删除其一不影响另一个。
- 自有 Catalog 中的展示组件、自定义输入、自定义 action 组件完成生成 → 输入 → handler → 同 surface patch，无需修改 SDK 内核。
- 非法组件、未声明 action、额外输入、越权路径、旧 revision、缺失 `done`、取消、慢消费和超限均有证伪测试。
- patch 或传输失败时，不把 SDK 失败推断为业务失败；使用宿主替身证明已执行副作用不会被 SDK 重放或回滚。
- 两个无关 Catalog 复用相同机制，不因请求中的搜索、表单、客户等业务词触发 SDK 特例。

验证宿主与 Agent 尚未选定；验收采用可替换的确定性接入夹具，不预设某个业务应用。真实业务应用仅提供额外集成反馈，其工程架构、业务表、状态机、结果查询与验收不属于 SDK 评审或整改范围，也不作为 SDK 发布的强制依赖。确定性 fixture 验证 SDK 契约；真实模型冒烟单独验证生成接入，不作为单元回归前提。

### 5.2 质量与发行

先交付上述可信接入切片，再发布标明支持子集和限制的 alpha。公开 alpha 前须关闭已知可达安全缺陷，完成当前产物仓外安装、关键失败路径、相关 typecheck/lint/test/build 和浏览器验收。正式发行与生产级设计达标声明还要求完整 CI、兼容/升级记录和资源边界证据。

workspace 直链、测试数量、旧 tarball 冒烟和业务演示成功不能替代当前产物门禁。接入重构前进行早期产物检查，公开 API 定型后再完成最终安装验收。具体阶段与完成状态只在 CURRENT 维护。

## 6. 非目标与取舍

首发集中于 React + Node、fetch/SSE 与版本化的 A2UI v0.9 子集。完整协议覆盖、Vue、多语言、WebSocket/A2A/MCP 适配、任意 FunctionCall、复杂表单平台、Agent 编排、通用认证、多租户 SaaS、分布式调度和业务持久化均不属于本轮目标。

保留受限标准组件作为可选默认能力；业务组件与流程通过宿主注册。先使用有界整树重建，不自研 reconciler；增加基本性能观测与资源上限，精细增量优化由真实瓶颈驱动。数据 schema 支持范围必须显式版本化，禁止默默忽略不支持的约束。
