# PRD — Nexus UI SDK

状态：产品边界与分阶段验收基线；✅ 表示源码和既有验证记录可支撑的能力，🚧 表示目标或待补闭环，进度证据以 [CURRENT](tasks/CURRENT.md) 为准。更新：2026-10-10。

## 1. 产品定位

**Nexus UI SDK 是主产品。** 它面向把 Agent 接入 Web 应用的宿主开发者，提供受约束的 A2UI Task Surface：接收候选消息、按协议与宿主声明校验、流式渲染、绑定用户输入、回传 action，并在同一 surface 更新结果。宿主保留组件选择、业务事实、权限和执行权。目标是可安装、可集成、可维护的 SDK，其公开边界和工程质量按生产级设计规范建设；不是只服务于仓内演示的 UI 代码。

这是个人开源项目，面试展示是项目用途，**不降低 SDK 的设计标准**。当前三包尚为私有包，部分能力仍在参考实现或规划中；“按生产级规范设计”是验收目标，不等于宣称当前版本已通过生产环境验证。支持的 A2UI v0.9 子集必须如实声明，不以“生产级”暗示完整协议覆盖。

OrderOps Copilot 是自建的验证 Agent 和宿主，不是另一款需要达到生产级的商业产品。它使用 mock 订单、SQLite、少量 fixture 和简化 Agent 流程，专门测试 SDK 在证据展示、动态组件、最新输入、人工确认、动作回流、失败恢复和跨流程复用中的边界。Agent 的模型质量、商户集成、业务规模和运营效果不作为 SDK 设计质量的替代指标。

**产品使用者与任务**：宿主开发者在自己的前后端注册组件及 action，接入自有 Agent，让模型输出可检查的任务界面；终端用户核对证据、编辑输入并确认；业务后端决定是否执行并返回结果。SDK 让开发者复用受控界面链路，而不是替宿主做业务决策。

**为什么不直接用官方 renderer 或完全自建**：官方实现按完整协议放行合法消息，而"官方合法"不等于本宿主的渲染器能安全消费全部特性，宿主仍要自建组件/字段准入与 action 回流（见 1.1 的自建成本）。Nexus 的差异点是受约束子集加分层准入：Protocol/Profile/Catalog/Policy 把协议合法性与宿主可用性分开裁决，越权输出在进浏览器前被 guard 拒绝，Host 保留事实与执行权威。宿主换取的不是更大的协议覆盖面，而是一条可检查、可拒绝、可恢复的接入链路（取舍见 [DESIGN](DESIGN.md) D3/D4）。

### 1.1 要解决的开发者问题

宿主开发者若自行接 A2UI，需要分别实现流式消息解析、组件/字段准入、渲染状态、输入绑定、action 来源校验与失败清理。这些代码跨浏览器与服务端，最容易在“界面已显示但尚未提交”“用户修改了输入”“业务已执行但响应断线”时出现不一致。Nexus 的产品承诺是让开发者在保留自己的业务后端和 UI 设计系统的前提下，复用一条**可检查、可拒绝、可恢复**的任务界面链路。

目标用户优先级：第一位是已有 React 应用与自有 Agent/后端的开发者；第二位是要把 Agent 输出接入现有业务流程的团队。OrderOps 运营人员是验证场景的终端用户，不是 SDK 的购买者或产品定位依据。首版只承诺 React + Node Host 的可验证接入，不承诺跨框架、跨语言或生产托管服务。

## 2. 产品形态与 SDK 框架

### 2.1 包与使用入口

| 产品层 | 宿主拿到什么 | 当前状态 | 目标边界 |
| --- | --- | --- | --- |
| `@nexus-ui/core` | JSONL 缓冲、协议/Profile/Catalog 校验、surface 状态、VNode、绑定与 action 事件 | ✅ 根入口和 API 版本存在 | 不依赖 React、DOM、Node 或具体 transport |
| `@nexus-ui/react` | Provider、标准 renderMap、自定义组件映射和输入控件 | ✅ 当前 17 个标准组件 | 可换宿主设计系统，错误/校验状态可访问 |
| `@nexus-ui/server` | AgentAdapter、guard、SSE、外部 Agent RPC、Catalog 发布与有限 Host 装配 | ✅ 有限公开根入口 | 不包含业务事实、授权和领域事务 |
| 浏览器接入能力 | 生成与 action transport、终态处理、surface 装配 | 🚧 目前散在示例中 | 宿主无需复制关键 SSE/回流/错误处理逻辑；是否新增 client 或组合组件待验证 |
| 服务端准入能力 | 在 Host 发送前拒绝不可信候选消息 | ✅ 参考 server 可用；🚧 非 Koa 宿主待验证 | 独立宿主可复用校验行为；是否拆出 guard 包待验证 |

面向宿主的预期接入顺序：定义 Catalog（组件 schema、policy、action）→ 注册 React renderMap → 配置 Agent 生成源、Policy 与本地 handler → 发布 Catalog Contract → 生成受控 surface → 用户输入/action → Host 执行并返回同 surface patch。每一步均经公开 API；基础组件不够时由宿主扩展 Catalog，而非修改 SDK 内核。结构和依赖方向见 [ARCHITECTURE](ARCHITECTURE.md)，wire/API 精确语义见 [SPEC](SPEC.md)。

**首个可用接入旅程**：在仓外干净 React + Node 项目安装 SDK，定义一个含文本、输入和确认按钮的自有 Catalog；接入一个确定性 Agent fixture 和本地 action handler；看到 `done` 后编辑输入、提交 action，并在同一 surface 看见结果。把生成错误、非法组件与断线样本代入同一接入，宿主能区分失败和已提交的业务结果。验收时记录依赖、接入步骤、需要宿主自行编写的胶水代码与实际命令；这也是是否需要新增高层 API 的判断依据。

| 能力域 | 使用场景与预期行为 | 范围/状态 |
| --- | --- | --- |

| Catalog 与扩展 | 宿主限定组件、props、绑定和 action；不认识或越权的输出有定位到字段的诊断 | ✅ 基础边界；🚧 path 级可编辑约束须明示由 Host 校验 |

| 包与版本 | 独立项目可安装类型和运行产物，检查 core/renderer/API/协议兼容 | ✅ `dist` 入口及历史冒烟；🚧 当前版本仓外安装与发行门禁 |

## 3. SDK 必须交付的能力

| ID | 能力 | 可验证结果 |
| --- | --- | --- |
| R1 | 受约束的协议运行时 | JSONL 跨 chunk 解析、v0.9 surface 生命周期、组件树/dataModel 更新；非法顺序和不支持特性有稳定诊断，不污染已提交状态 |
| R2 | 宿主可声明的能力边界 | Catalog 组件 schema、字段/绑定/action policy 与 prompt contract 同源；越权输出在进入浏览器前被 guard 拒绝，prompt 不能替代 guard |
| R3 | 框架适配与可定制渲染 | core 不依赖 UI 框架；React 宿主可替换 renderMap 接入自身设计系统，输入按声明写回，具备基本可访问性；第二渲染器不是首发门禁 |
| R4 | 可组合的生成与交互 | 宿主可接自有 Agent、transport、history、policy 和 action handler；生成、确认、同 surface patch 走公开入口，业务模型不进入 SDK |
| R5 | 明确的失败和执行语义 | 校验/提交失败不留可执行 action；并发、重复、取消、超时、断线和提交后响应失败都有可观察结局；SDK 不把内存 ledger 宣称为领域事务 |
| R6 | 可安装与兼容 | 包仅经公开根入口消费，类型、exports、产物与依赖可在仓外干净宿主安装；协议版本、包版本、API 版本和兼容范围明确，破坏性变更可识别 |
| R7 | 可诊断与可验证 | 结构化 diagnostics、conformance 偏差基线、非法输入与资源上限的证伪测试、独立宿主端到端用例和 CI 门禁可复现 |

当前 core、React 和有限 server 装配入口是 SDK 的实际基础。首版必须让独立宿主通过公开入口完成生成、受控渲染、交互和结果回流，并能识别终态与错误；浏览器 client、`NexusSurface`、独立 guard 包只是可能的 API 形状。若现有入口和少量宿主代码已能稳定完成接入，就不为包数量或组件命名另设验收门槛。Vue、完整官方 Basic Catalog、更多业务组件不属于首个生产级设计验收范围。

## 4. 生产级设计验收线

这里的“生产级”约束 **SDK 自身**：

1. **边界可审计**：协议、Profile、Catalog、Policy、Renderer 职责分开；不可信 Agent/浏览器输入、宿主事实与副作用各有明确所有者；限制消息大小、耗时和资源消耗。
2. **失败可恢复**：流式预览与已提交 surface 区分；取消、重复 action、并发与部分提交有明确状态及测试。业务事务由宿主负责，SDK 提供足够的钩子、错误和状态让宿主恢复。
3. **兼容可管理**：支持子集、公开 API、版本兼容和迁移规则成文；协议升级不静默改变既有行为。包产物在独立宿主验收，而非只靠 monorepo 路径工作。
4. **集成可操作**：外部宿主能够只依赖公开入口完成 Catalog 注册、受控渲染、Agent 接入、用户输入、action 与 patch；文档和示例覆盖正常路径与典型坏输出。
5. **质量可复现**：conformance、资源/安全反例、类型检查、lint、构建、单元与跨包测试、浏览器关键流程和干净安装门禁均有记录。失败与诊断能定位到具体消息或字段。

以上是对外声称”SDK 生产级设计达标”的门禁，不要求本项目建设通用认证、多租户、支付、持久化业务系统或生产级 Agent 服务；这些属于宿主部署/业务边界。**优先级排序**：标明限制的 alpha 是本项目的预期发布形态，首条业务闭环后即评估发布，独立接入与演示旅程优先于完整发行门禁；”生产级设计达标”是长期目标，不作为当前迭代的排期前提。alpha 必须清楚标注支持子集和未通过的门禁；正式 npm 发布与达标声明须有独立安装和完整质量证据，不以 OrderOps 单一演示成功替代。

| 非功能维度 | 验收方式 | 当前差距 |
| --- | --- | --- |
| 有界资源 | 非法 JSON、超长行/响应、超时、慢连接和恶意 checks 输入触发限制且不挂死宿主 | 核心与 RPC 已有部分上限；需覆盖组合路径与浏览器 client |
| 兼容性 | API 快照、协议 conformance、包版本检查和升级说明；破坏性变更显式版本化 | 当前基线存在，正式发行流程未闭合 |
| 可靠性 | SSE `done/error/中断`、action 并发/重复/取消和 commit 失败有状态与回归用例 | 取消和领域提交后的恢复未完整验收 |
| 宿主体验 | 干净项目只用根入口完成自定义 Catalog、renderMap、Agent、action 与 patch | 旧 tarball 冒烟存在，新快照尚待独立重验 |
| 可访问性 | 输入标签、错误反馈、禁用态与键盘交互在真实浏览器检查 | 现有 React 控件有基础实现，业务组合尚待验收 |

首发不设渲染性能与包体积门槛；上表的资源约束指协议/HTTP 边界的输入上限（见 [SPEC](SPEC.md) §3），不含渲染性能指标，后者由真实消费方反馈驱动再立项。

## 5. 验证场景与业务流程

**独立宿主**验证 SDK 的可安装和可替换性：自有 Catalog/renderMap/Agent endpoint/handler 只用公开入口，完成生成 → guard → 渲染 → 输入 → action → patch，并注入非法组件、错误信封和断线等失败样本。

**OrderOps 第一流程（M1–M3）**使用确定性规则检测物流停滞，Agent 从只读快照引用事件、解释原因并建议建单；运营人员修改备注并确认 `createTicket`，Host 校验最新输入和案件版本、幂等创建模拟工单，断线或刷新后查询真实结果。正常对照、编造证据、旧 surface、双击和 patch 失败都进入测试。真实模型只需单独冒烟验证接入，CI 用确定性模式保持复现。

### 5.1 物流停滞：从发现到建单

| 步骤 | 运营人员看到/操作 | Host / Agent / SDK 责任 | 阶段 |
| --- | --- | --- | --- |
| 1. 发现 | 队列列出待处理案，可按状态、严重度筛选并搜订单号；正常订单不出现 | Host 按最近有效物流事件与阈值确定性建案，重复扫描不重复建案 | ✅ M1 |
| 2. 核对 | 详情显示订单金额、承诺送达、触发事件和时间线；事件 ID 可回查 | Host 提供权威订单与来源；稳定导航和队列是宿主 UI | ✅ M1 |
| 3. 分析 | 点击分析后展示原因、建议、证据引用和不确定性；证据不足有明确状态 | Agent 经只读工具取快照并校验证据 ID；SDK guard 只接纳 Catalog 内的组件和字段 | 🚧 M2 |
| 4. 审核 | 在动态 surface 编辑备注，提交前可重新核对证据；流未完成时不能点击业务按钮 | React 绑定最新值；Host 只接受声明过的备注，案件 ID 从服务端关联取 | 🚧 M2/M3 |
| 5. 执行 | 明确确认后看到工单号、已建单状态及不可重复操作的按钮 | Host 校验案件版本并事务写工单/操作/审计；SDK 校验 action 并下发同 surface patch | 🚧 M3 |
| 6. 恢复 | 刷新或断线后仍能查询实际工单结果，失败不会误报成功 | Host 案件/操作查询是最终事实，Web 不盲目重发建单 | 🚧 M3 |

首条 fixture 是停滞订单与正常对照订单。检测器以最新事件判断，事件无效或缺失时跳过而不让模型补造。业务 UI 分工固定：队列、详情、路由和操作状态属于宿主；订单摘要、物流时间线、分析说明、备注和确认按钮进入 Nexus surface。首条 Catalog 只开放六种组件与 `createTicket`，不把未来退款组件提前加入当前契约。

### 5.2 高金额退款：验证第二种交互

M4 构造高金额退款申请，运营人员先看订单金额与风险提示，再编辑拟退款金额和理由，明确确认模拟退款。Host 从数据库重读可退余额/订单状态，校验金额上限、案件版本与重复请求，在本地事务记录模拟结果；SDK 继续使用同一套 Catalog 扩展、绑定、guard、action 回流和 patch 机制。金额、币种和可退范围绝不以 Agent 或浏览器字段为权威。此流程当前只是目标设计，退款阈值与字段格式应在 M4 实施前于 SPEC 锁定，不把未定值写成已实现事实。

| 验证点 | 物流建单 | 模拟退款 |
| --- | --- | --- |
| 动态内容 | 物流证据与建单建议 | 风险提示、金额与退款建议 |
| 人工输入 | 备注 | 金额与理由 |
| Host action | `createTicket` | 目标 `approveSimulatedRefund` |
| 共同 SDK 能力 | Catalog、guard、绑定、确认、同 surface patch、失败诊断 | 同左；不得新增 OrderOps 专用分支到 Nexus 包 |

OrderOps 验证通过说明 SDK 能覆盖这些代表性工作流；仍需独立的 API、兼容、产物、边界和失败门禁，才能声称 SDK 达到目标。反过来，OrderOps 不需要真实商户数据或生产级 Agent 才能验证 SDK 的工程边界。

## 6. 优先级、验收与非目标

SDK 的验收证据以公开入口的仓外干净安装、独立宿主与 OrderOps 两类消费方、协议/Profile/Catalog 反例、action 失败路径、兼容性快照和 CI 为主。当前实现与待办分别见 [SPEC](SPEC.md) 和 [CURRENT](tasks/CURRENT.md)。商业指标（建议采纳率、处理时间、退款损失）须有真实参与者和人工基线；mock 演示不报告真实业务收益。

下表是**产品验收优先级，不是下一次迭代的任务量**。P0 由 M2 接线、M3 建单与独立宿主验收逐段累积；每段只实现和验证它实际触及的 R1–R7 行为，最后才判断 P0 是否整体通过。当前唯一执行顺序与阶段出口见 [CURRENT](tasks/CURRENT.md)，不得把整张 P0 表当成一个开发任务。

| 优先级 | 对外可交付结果 | 完成判据 |
| --- | --- | --- |
| P0：首个可信 SDK 切片 | 独立宿主接入 + OrderOps 物流建单闭环；SDK 的协议、Catalog、action 与失败边界可审计 | R1–R7 在首条切片的反例、仓外产物安装和公开入口验收通过；M3 业务成功、重复与断线恢复有真实结果查询 |
| P1：通用性与发行 | 第二种金额输入/action 流程证明无业务硬编码；补齐浏览器接入复用、兼容与发布门禁 | M4 共用同一 SDK 机制；浏览器关键流程、版本升级/发布记录通过，才可声称设计达标 |
| P2：扩展 | Vue、更多组件、更多异常或报表 | 由新消费场景驱动，不阻塞首版 |

成功标准是可复核的接入结果：独立宿主只依赖根入口完成上述旅程，非法候选消息不能产生可执行 action，用户最新输入抵达 Host，断线后能查到领域终态；两种业务流程不要求 Nexus 包出现 OrderOps 类型。仓内演示、测试数或面试叙述均不能单独替代这些证据。

| 验收线 | 阶段 | 关口 |
| --- | --- | --- |
| SDK 协议与边界 | 已有 Layer 0 / conformance → R1/R2/R5 | 偏差显式声明；错误、取消、资源和坏输出反例全绿 |
| SDK 接入与发行 | R3/R4/R6/R7 | 仓外安装、公开 API 与兼容检查、独立宿主全流程、版本/发布记录；高层 API 以接入重复点定型 |
| 业务验证 1 | OrderOps M0–M3 | 从停滞事实到人工建单、结果恢复闭环；当前只完成 M0/M1 |
| 业务验证 2 | OrderOps M4 | 用金额输入和不同 action 证明 SDK 复用，无通用包业务特例 |

SDK 首个目标不做通用 prompt-to-UI 平台、任意 A2UI v0.9 特性兼容、多租户 SaaS、支付执行、完整 BI 或生产 Agent 托管。架构拓扑见 [ARCHITECTURE](ARCHITECTURE.md)，设计取舍见 [DESIGN](DESIGN.md)。
